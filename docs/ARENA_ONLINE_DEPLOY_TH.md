# ติดตั้ง Arena ออนไลน์ V6 — สำหรับเจ้าของระบบ

**IMPLEMENTED — NOT TESTED — OWNER QA REQUIRED**

โค้ดถูกเพิ่มแล้ว แต่ยังไม่ได้รัน migration ตั้งค่าโฮสต์ เปิดระบบออนไลน์ หรือทดสอบใด ๆ เอกสารนี้เป็นขั้นตอนให้เจ้าของพิจารณาและดำเนินการเอง ไม่ใช่รายงานว่าติดตั้งสำเร็จแล้ว

## รูปแบบระบบที่เลือก

ต่อยอด Next.js Node server และ SQLite กลางเดิม ไม่สร้างระบบบัญชีหรือฐานข้อมูลชุดที่สอง ผู้เล่นทุกเครื่องต้องใช้ URL เดียวกันและเข้าถึงเซิร์ฟเวอร์ตัวเดียว ซึ่งอ่านไฟล์ฐานข้อมูลถาวรไฟล์เดียว เซสชัน ผู้เล่น สหาย รอบแข่งขัน และฤดูกาลอยู่ฝั่งเซิร์ฟเวอร์ทั้งหมด localStorage เดิมใช้เฉพาะการฝึกและความสะดวก ไม่ใช่หลักฐานอันดับ

รูปแบบนี้รองรับการติดตั้งเซิร์ฟเวอร์กลางหนึ่งชุด ไม่ใช่ฐานข้อมูลหลายภูมิภาคหรือการกระจายหลาย instance และยังไม่ได้วัดขีดจำกัดการรับโหลด หากต้องขยายหลาย instance ต้องย้ายชั้นข้อมูลอย่างมีแผนไป PostgreSQL/บริการฐานกลางที่รองรับ ห้ามให้หลายโฮสต์สร้างไฟล์ SQLite ของตนเองแล้วเรียกว่าใช้ข้อมูลเดียวกัน

**ไม่ควรนำไฟล์ SQLite ไปไว้ใน deployment filesystem ชั่วคราวของ serverless หรือ static hosting** เช่นการ deploy หน้าเว็บอย่างเดียวแล้วคาดว่าฐานข้อมูลจะคงอยู่ ต้องมี Node runtime ที่รองรับ `node:sqlite` และ storage ถาวรนอก `public` โฮสต์เดิมจะรองรับหรือไม่ยังไม่ได้ตรวจ

## สิ่งที่เจ้าของต้องจัดเตรียม

1. โฮสต์ Node ที่เข้าถึงได้จริง รองรับ `node:sqlite` และให้ app instance เดียวเป็นตัวเขียนฐานข้อมูล
2. พื้นที่เก็บฐานข้อมูลถาวร สิทธิ์ไฟล์จำกัดเฉพาะบัญชีบริการ สำรองข้อมูลและตรวจการกู้คืนได้
3. โดเมน/ที่อยู่ HTTPS และ reverse proxy ที่ส่ง Host/Origin อย่างถูกต้อง
4. ค่ากำหนดที่ inject จากโฮสต์ ไม่ใส่ใน Frontend หรือ Git
5. ตรวจ migration และสร้าง consistent backup ก่อนเพิ่มโครงสร้าง V6

ไม่มีการซื้อบริการ ติดตั้ง provider ใหม่ หรืออ่านรหัสจาก `.env.local` ในงานนี้

## ชื่อตัวแปรที่ใช้จริง

ไฟล์ `.env.example` มีเฉพาะชื่อและช่องว่าง:

- `ARENA_DB_PATH` — absolute path ของฐานข้อมูลส่วนตัวบนเซิร์ฟเวอร์
- `ARENA_PUBLIC_ORIGIN` — origin กลางจริง ต้องเป็น HTTPS ใน production และไม่มี path/ท้าย slash ที่ไม่ตรง Origin

`NODE_ENV` ใช้ตามกลไก Next.js/โฮสต์เดิม ไม่เพิ่ม `NEXT_PUBLIC_` สำหรับรหัสลับ ไม่มี `service_role` หรือ connection string ฝังในเบราว์เซอร์ ระบบเดิมใช้ opaque random session เก็บ hash ในฐานข้อมูล จึงไม่ได้เพิ่ม `SESSION_SECRET` ที่ไม่มีส่วนใช้งานจริง

ใน production หากไม่ได้กำหนด `ARENA_PUBLIC_ORIGIN` หรือไม่ใช้ HTTPS คำขอแก้ข้อมูลจะถูกปฏิเสธ ห้ามแก้โดยปลดการตรวจ Origin หรือเอา Secure cookie ออก

## เพิ่มโครงสร้างฐานข้อมูล — ยังไม่ได้รัน

ไฟล์ที่ต้องตรวจ:

- `server/arena/schema.sql` — โครงสร้างเดิมเวอร์ชัน 1 ไม่ถูกแก้ย้อนหลัง
- `server/arena/migrations/002-online-ranked.sql` — เพิ่มโครงสร้างจากเวอร์ชัน 1 เป็น 2
- `scripts/migrate-arena-v6.mjs` — ตัวรันสำหรับเจ้าของ ไม่ถูกเรียกตอนเปิดแอป

ผลกระทบ: เพิ่มความยินยอมเข้าทำเนียบให้ผู้เล่นโดยค่าเริ่มต้นเป็นปิด เพิ่มข้อมูลการรับรองผลและฤดูกาล ตารางฤดูกาล อันดับที่บันทึก รหัสกู้คืน คำขอสร้างรอบ คิวตรวจ และดัชนี ไม่มี DROP/TRUNCATE หรือล้างประวัติเดิม ไม่มีผู้เล่นหรือผลแข่งขันตัวอย่าง และไม่แปลงผลเก่าเป็น VERIFIED

ดัชนีคู่สหายบังคับให้คู่ A–B และ B–A ซ้ำกันไม่ได้ ถ้าฐานเดิมมีคู่กลับด้านซ้ำ migration จะหยุดทั้ง transaction เจ้าของต้องตรวจข้อมูลและเตรียม corrective migration เฉพาะกรณี ไม่ให้สคริปต์เลือกลบคำขอให้เอง

ให้เจ้าของเปิด PowerShell ตรวจว่าอยู่ใน `D:\etcstream` และกำหนด environment ให้ชี้ฐานข้อมูลที่ถูกต้องก่อน พิจารณาสำรองและหยุด app writers รวมถึง process อื่นที่ใช้ฐานนี้ จากนั้นจึงรันด้วยตนเอง:

```powershell
node scripts/migrate-arena-v6.mjs --owner-reviewed-and-backed-up
```

คำสั่งนี้เปลี่ยนฐานข้อมูลจริงและยังไม่ได้รันโดยผู้พัฒนา หากเป็นการติดตั้งใหม่ต้องใช้ขั้นตอน provision เดิมโดยเจ้าของก่อน แล้วจึงเพิ่ม V6 การ provision ผู้ดูแลต้องกรอกรหัสในหน้าถามแบบซ่อนเท่านั้น ไม่ใส่รหัสในคำสั่งหรือแชต และไม่เปิดบัญชีผู้ดูแลผ่านชื่อเล่น

## สำรองและกู้คืน

- สำรองแบบ SQLite consistent backup โดยเครื่องมือของผู้ดูแล หรือหยุด app/ตัวเขียนทั้งหมดให้เรียบร้อยก่อนสำรอง ห้ามคัดลอกเฉพาะไฟล์หลักขณะ WAL ยังมี transaction ค้าง
- เก็บ backup นอก `public` และนอก repository ควบคุมสิทธิ์และอายุการเก็บ เพราะมีข้อมูลผู้เล่น hash เซสชัน และ hash รหัสรับรอง
- ก่อนกู้คืน หยุดแอปและตรวจว่าเลือก backup/สภาพแวดล้อมถูกชุด จัดการ WAL/SHM ของชุดเดิมตามขั้นตอนของเครื่องมือ ห้ามผสมไฟล์ฐานหลักกับ WAL คนละชุด
- การกู้ backup ย้อนหลังอาจทำให้เซสชัน/รหัสกู้คืนที่เคยยกเลิกกลับมามีผล ต้องเตรียมนโยบาย revoke และแจ้งผู้ใช้โดยเจ้าของ
- ยังไม่มีการรัน backup/restore หรือทดสอบการกู้คืนในงานนี้

## เปิดให้หลายเครื่องใช้งาน

- ทุกคนเปิด HTTPS origin เดียวกัน จึงใช้ผู้เล่น สหาย และฤดูกาลชุดเดียว
- `localhost:3000` บนอีกเครื่องหมายถึงเครื่องนั้นเอง ไม่ใช่เครื่องที่โฮสต์เกม
- การสาธิต LAN ต้องใช้ที่อยู่เครื่องโฮสต์ที่เข้าถึงได้และตั้งค่า origin/ไฟร์วอลล์ให้ตรงเฉพาะเครือข่ายที่อนุญาต Production ใช้ HTTPS เพื่อ Secure cookie
- ห้ามนำ SQLite ไปวางในโฟลเดอร์หน้าเว็บหรือเปิดไฟล์ฐานข้อมูลให้ผู้เล่นดาวน์โหลด
- ชื่อเล่นซ้ำได้ แต่ตัวตนคนละชุด ใช้ immutable player ID ที่เซิร์ฟเวอร์ออกให้ ไม่ค้นผู้เล่นเดิมด้วยชื่อเพื่อรับสิทธิ์

## ย้ายตัวตนและรหัสกู้คืน

ผู้เล่นที่ล็อกอินอยู่สร้างรหัสส่วนตัวได้จากโปรไฟล์ หลังยืนยันความเสี่ยง รหัสสุ่ม 32 bytes ถูกแสดงครั้งเดียวในหน้าและเก็บเฉพาะ SHA-256 hash ในฐานข้อมูล ใช้ได้ครั้งเดียวภายใน 30 วัน การสร้างใหม่ยกเลิกรหัสกู้คืนเก่า

เครื่องใหม่ที่ยังไม่มีตัวตนใช้แบบฟอร์มกู้คืน ระบบยกเลิกเซสชันเดิมทั้งหมดแล้วออกเซสชันใหม่ เป็น **การย้าย/กู้คืน ไม่ใช่การรวมบัญชีหรือเพิ่มหลายเครื่องพร้อมกัน** ถ้าเครื่องปลายทางมีผู้เล่นอยู่แล้วต้องออกจากตัวตนนั้นเองก่อน รหัสสหายใช้เข้าสู่ระบบไม่ได้ ผู้เล่นที่ไม่มีทั้งเซสชันและรหัสกู้คืนที่ใช้ได้ยังไม่มีการกู้ด้วยชื่อ/อีเมล ต้องแจ้งข้อจำกัดตามจริง

ห้ามบันทึกรหัสกู้คืนใน log, analytics, URL, รายชื่อสาธารณะ หรือช่องรหัสสหาย

## อันดับรายด่านและฤดูกาล

- ทำเนียบรับหนึ่งผลดีที่สุดต่อผู้เล่นต่อด่านและเวอร์ชันกติกา เฉพาะ VERIFIED ที่ไม่ถูกยกเลิก มี `verified_at` และ `validation_version` พร้อมเวลาที่สอดคล้องกัน
- เรียงเวลารวม → บทลงโทษ → เวลาจริง → เวลารับรอง → รหัสผล อันดับสหายคำนวณเฉพาะความสัมพันธ์ accepted กับตัวเอง พร้อมแสดงอันดับทั้งหมดแยก
- รอบตัวข้าใช้ช่วงอันดับทั้งหมด ±3 จาก SQL ฝั่งเซิร์ฟเวอร์ ไม่ดาวน์โหลดทั้งตารางมาคำนวณในเบราว์เซอร์
- อันดับมี pagination 25 รายการและ `hasMore/nextOffset` จริง การอัปเดตใช้ polling เมื่อเปิดหน้า พร้อมถอยระยะเมื่อเชื่อมต่อผิดพลาด ไม่ใช่ WebSocket หรือรับประกันเวลาจริงระดับมิลลิวินาที
- Presence เดิมต่ออายุ heartbeat ราว 30 วินาที เกิน 90 วินาทีถือว่าไม่แสดงออนไลน์ และต้องมีความยินยอมจริง
- ต้องเปิดทั้งรายชื่อและความยินยอมแรงก์จึงอยู่ในกลุ่มจัดอันดับ การปิดความยินยอมไม่ลบประวัติส่วนตัว แต่มีผลต่อกลุ่มผู้เข้าเกณฑ์และคะแนนในฤดูกาลที่ยังไม่ปิด
- ไม่สร้างฤดูกาลอัตโนมัติ ผู้ดูแลใช้ `/admin` → ห้องแข่งขัน → ฤดูกาลและแรงก์ กำหนดชื่อและเวลา กติกา V1 กับ 25 เวอร์ชันด่านถูกตรึงตอนสร้าง เปิดล่วงหน้าได้แต่เริ่มรับตามเวลาจริง
- สูตรต่อด่านคือ round(1000 × (N−r+1)/N) รวม 5 ด่านต่างกันที่ได้คะแนนมากที่สุด สูงสุด 5000 เล่นซ้ำไม่สะสมเพิ่ม ชั้นแรงก์และเงื่อนไขชั่วคราวอยู่ใน `game/content/arena-ranked-rules.ts`
- คะแนนเท่ากันใช้จำนวนด่านยืนยันมากกว่า เวลาที่ได้ชุดผลครบก่อน และ immutable player ID การมีผลยืนยันเพิ่มเติมอาจเปลี่ยนตัวตัดสินเมื่อคะแนนเท่ากัน นโยบายนี้เป็นส่วนหนึ่งของ V1
- ผู้ร่วมฤดูกาลน้อยกว่า 3 คน ผู้เล่นครบไม่ถึง 3 ด่าน หรือด่านที่นำมาคิดมีคู่แข่งน้อย จะแสดงอันดับชั่วคราว คะแนน 1000 จากผู้แข่งขันคนเดียวไม่ใช่ใบรับรองทักษะ
- เมื่อถึงเวลาสิ้นสุด ผู้ดูแลปิดฤดูกาลเพื่อ snapshot ทั้งคะแนนและอันดับรายด่าน พร้อมเก็บผลอ้างอิง ไม่ปรับกติกาหรือ rescore ประวัติที่ปิดแล้ว การปกปิด/ระงับและยกเลิกหลักฐานยังถอนการแสดงรายการที่ไม่เข้าเกณฑ์ได้ โดยไม่เปลี่ยนคะแนนหรือเลื่อนอันดับที่บันทึกของผู้อื่นย้อนหลัง
- ฤดูกาลใช้เฉพาะรอบที่ถูกผูกกับฤดูกาลขณะสร้าง เริ่มสร้างหลังเวลาเปิด จบและได้รับการรับรองก่อน cutoff ผลเก่า/ผลที่รับรองช้าไม่ถูกย้ายเข้าฤดูกาลย้อนหลัง

## จุดที่ยังบล็อกการแข่งขันจัดอันดับจริง

**ยังไม่มี authoritative gameplay command replay ครบทุกการกระทำของระบบฝึก** การตรวจกราฟที่ส่งจากเบราว์เซอร์แม้ผ่าน ก็ไม่พิสูจน์ว่าผู้เล่นทำตามกระบวนการจริง จึงยังให้ผลส่งเป็น UNDER_REVIEW ทุกครั้ง ไม่มี endpoint ผู้เล่นหรือปุ่มผู้ดูแลที่แอบตั้ง VERIFIED เพื่อเติมทำเนียบ

โครงสร้างและตัวคำนวณอันดับพร้อมรับผลยืนยัน แต่ยังไม่มีเส้นทาง gameplay ที่ออกหลักฐาน VERIFIED ได้ในงานนี้ การเปิดฤดูกาลอย่างเดียวจึงไม่ทำให้มีคะแนน คิว `/admin` → ห้องแข่งขัน → คิวตรวจผล ดูผลเดิม/ใหม่และปฏิเสธพร้อมเหตุผลได้ ไม่ใช่กลไกยืนยันแทนหลักฐาน

Duel ยังปิด ไม่มีห้อง คู่แข่ง หรือผลผู้ชนะจำลอง การเปลี่ยนเป็น authoritative game server และซิงก์การแข่งขันสองคนยังเป็นงานที่ไม่ได้ทำในรอบนี้

ยังไม่มีบันทึกส่วนต่างคะแนนก่อน/หลังแต่ละรอบ ไม่มีกราฟประวัติแต้มย้อนหลัง ไม่มี provider realtime และไม่มี deployment หลาย instance ระบบไม่สร้างค่าพวกนี้มาทดแทน

- [ ] สำรองฐานเดิม อ่าน migration และตรวจกรณีข้อมูลซ้ำ ก่อนสั่งเพิ่มโครงสร้างด้วยตนเอง
- [ ] ใช้สองอุปกรณ์จริงกับ HTTPS origin เดียว ตรวจว่าได้คนละ player ID แม้ชื่อซ้ำกัน
- [ ] ส่ง/รับ/ยกเลิกคำขอสหาย ปิดกั้น และเปิด/ปิดความยินยอม Presence/ทำเนียบ
- [ ] สร้างและใช้รหัสกู้คืนที่เก็บอย่างปลอดภัย ตรวจว่ารหัสเดิมใช้ซ้ำไม่ได้และเซสชันเก่าถูกยกเลิก
- [ ] ตรวจทุกด่าน ตัวเลือกกติกา pagination อันดับของฉัน สหาย และรอบตัวข้า เมื่อมีผลยืนยันที่มาจากเส้นทาง authoritative ที่เจ้าของตรวจรับในอนาคต ห้ามสร้าง VERIFIED ปลอมเพื่อกล่าวว่าระบบสำเร็จ
- [ ] ตรวจว่า DNF/REJECTED/UNDER_REVIEW ไม่ให้แต้ม และผลเก่าไม่มีหลักฐานไม่กลายเป็นอันดับ
- [ ] ตรวจสร้าง/เปิด/ปิด/เก็บฤดูกาล ความคงที่ snapshot การถอนสิทธิ์แสดงผล และ audit
- [ ] ตรวจสิทธิ์ `/admin` และคำขอจาก origin อื่น รวมการหลุดเชื่อมต่อและ retry

## ผู้ดูแลสามห้อง V8 (แทนพฤติกรรมการเข้าของ V7)

เข้า `/admin` ต้องกรอกรหัสหลักใหม่ทุกการเปิดจากภายนอก/รีเฟรช ภายในมีห้องแข่งขัน ห้องฝึก และห้องภารกิจ การเล่นตรวจของผู้ดูแลอยู่ในหน้าเดียวและไม่ส่งคะแนน ห้องแข่งขันต้องยืนยันรหัสแยกก่อนเรียก API จัดการทุกชนิด การตั้งค่ารหัสแยกไม่แก้ฐานข้อมูลหรือรหัสหลัก โปรดอ่าน `scripts/provision-competition-code.mjs` และรายงาน `ETCSTREAM_ADMIN_V8_IMPLEMENTATION_TH.md` ก่อนเจ้าของรันเอง ไม่ส่งรหัสให้ agent

สิทธิ์ห้องแข่งขันและการเล่นตรวจเก็บชั่วคราวใน process ของเซิร์ฟเวอร์ รีสตาร์ตต้องเข้าสู่ระบบใหม่ ใช้ Node instance เดียวกับฐานข้อมูล SQLite แบบ persistent ตามระบบเดิม ไม่ควร deploy หลาย instance หรือ serverless โดยยังไม่มี shared grant store การปิดแท็บส่งคำขอออกแบบ best-effort; การออกผ่านปุ่มจะรอการเพิกถอนจริง
